# 2026-11-08：日常对话优先的质量提升方案

目标：重点提升自然、简洁、能承接前文的日常对话，同时补强并保留常识、基础推理、指令遵循和编程。当前证据支持先调整会话上下文、训练内容和评测，再决定更长训练或架构迁移。

## 本轮实测

固定读取第 6000 步 best，源码 `fce3b4b`，BF16、无惩罚 greedy，不更新权重。240 道程序诊断按十任务×中英两语言×每格三例构造；另做 22 个日常、推理、代码探针和一组近期历史对照。模型文件的 inode、大小和修改时间均保持一致。

| 诊断条件 | 正确数 | 内容 CE，不含 EOS |
|---|---:|---:|
| 从已消费的 96000 行中抽取训练原题 | 40/60 | 0.715 |
| 内部验证，内容家族留出 | 34/60 | 1.005 |
| 原固定外部监控 | 24/60 | 2.184 |
| 同一外部题，只替换为熟悉的训练措辞 | 33/60 | 1.369 |

这不是四个独立盲测集：后两组是配对诊断，原监控也已多次用于择模。结果说明模型有明显的措辞敏感性，同时内容/算法学习不足：抽取的已训练算术题为 0/18；反转为训练 6/6、内部留出 3/6、原外部 0/6、重措辞外部 1/6。不能把全部失败归因于未见数字或某一个解码参数。

EOS 的预测比答案内容容易得多：内部验证的 EOS CE 约 0.00062，答案内容 CE 约 1.005。低整体 CE 和 EOS 100% 都不能替代正确内容。当前数据已按样本平均 CE 训练，best 也按每样本 CE 选择；旧的“长答案 token 权重压倒目标”缺陷不能直接作为本轮原因。

自然语言探针仍见复述用户、角色混淆、循环套话和翻译失败。6 个小型编程探针都没有完整满足要求；例如要求定义 `add` 只返回 `add(a, b)`，要求反转字符串却返回 `text.lower()`。代码只做语法解析及人工核读，没有执行，不能将这些结果等同于标准编程基准；目前编程能力需要补强，不能假定已经具备稳定水平。

详细结果、回答、任务分项和损失分解见 [quality_diagnosis_20261108.json](quality_diagnosis_20261108.json)。

## 关键原因及判断边界

1. **训练内容与日常聊天用途不匹配。** 100000 行中 68000 行是程序任务，32000 行是公共指令；只有 1961 行是多轮。显式英文 everyday-conversations 来源只有 761 行，不能把这个数字解释为所有中文/英文日常对话的总量。编程没有独立配额；1213 行含代码围栏只是文本指示，尚非核验过的编程题数量。
2. **当前服务缺少近期对话输入。** `stream_interact_and_evolve()` 只编码本轮 prompt，客户端也只发送本轮消息。当前 SFT 检查点不能在线写入快权重，因此同一 user_id 不会自动获得可用的跨轮语义记忆。对照中不带历史会编造偏好；显式提供历史后能取出姓名，但仍漏答颜色。应先提供可控的近期上下文，再单独验收长期快权重记忆。
3. **基础训练预算有限。** 完成的预训练是 100000×32768=3.2768B token、1024 序列；总参数 1.584B，语言阶段实际参与梯度约 1.138B，约 0.446B writer 参数留待元训练。原 uTTT 论文的 760M 实验使用 42.9B token 和 32768 上下文。两者架构和目标不完全相同，不能直接推导所需预算或承诺训练到某个 token 数就能达到论文结果。[uTTT，附录 D](https://arxiv.org/html/2610.05484v1)
4. **Surprise 不是聊天质量目标。** 当前关闭的是语言准备阶段的快权重写入，不能靠降低门限或增加重构辅助权重获得对话、逻辑和代码能力。长期记忆应在合格的语言底座上，通过外层任务损失经过可微写入来训练，并比较动态/冻结对照。

旧 Context Category 前缀清理在当前数据中命中 0 行，本轮没有据此修改数据清理或归因为当前质量问题。

## 下一阶段推荐

先采用以下**样本采样概率**作为起点，不把它们称为已验证最优比例。每样本 CE 保留现有协议，另记录实际监督 token、完整 EOS 比例和训练时间。

| 方向 | 起始占比 | 内容与验收 |
|---|---:|---|
| 日常对话 | 60% | 简短交流、自然建议、澄清、情绪回应、翻译；增加完整多轮承接和事实纠正，避免机械共情与重复套话 |
| 通用指令与基础推理 | 20% | 常识、时间/数量关系、简单逻辑、格式约束；算术从简单可核验题递进，不先大量堆三位数 |
| 编程 | 20% | 以 Python 基础函数、数据处理、读代码和修错为主，补常用脚本；答案须有独立测试，保留说明和必要边界条件 |

多轮建议先覆盖全部样本的 25–35%，作为与当前约 2% 的对照；优先保留完整短会话，而非复制少数长会话或截取其开头。中文为主，英文与代码保留；语言比例需与实际使用匹配。

数据选择应按用途、难度、质量和完整性取样，不能只按“短”或来源文件配额。可参考小模型短对话数据设计，但英文数据不能单独解决中文日常表达。[Smol-SmolTalk 官方说明](https://huggingface.co/datasets/HuggingFaceTB/smol-smoltalk)；完整 SmolTalk 还明确包含独立的数学与代码来源，而本项目先前只下载了三个英文子集。[SmolTalk 数据组成](https://huggingface.co/datasets/HuggingFaceTB/smoltalk)

使用教师模型补中文短多轮、澄清和代码示范时，先建立场景族并留出整族；过滤事实错误、程序测试失败及相似度过高的样本。离线生成可避免教师与训练进程争用显存。序列示范 SFT 是第一步；完整 logits 蒸馏或 on-policy 蒸馏属于独立实验，不应将“教师回答训练”称为复现了这些方法。[MiniLLM](https://arxiv.org/abs/2306.08543)

## 小实验和验收顺序

1. **先记录现有候选的日常/推理/代码基线。** 最新程序题 best 不必然是最适合聊天的初始化；至少比较最近 2000/6000 步模型的同一组自然语言与代码任务。
2. **补会话上下文。** 使用用户/会话隔离的、按 token 预算保留完整轮次的近期历史；支持清空，限制总预算。近期文本上下文和长期快权重记忆分别评测，不用前者证明后者。
3. **同父权重的小规模数据 A/B。** 两组都从同一权重重新初始化同样的优化器，固定学习率、预算和评测；比较当前配比与 60/20/20。新数据不能冒用原阶段完整状态续训。先做 500–1000 步诊断，再按结果扩大；该范围是建议，尚未启动。
4. **建立能力保留指标。** 对话看连贯、角色一致、具体性、简洁、澄清和多轮事实；推理看分任务正确率；编程看隔离环境中独立测试的通过率，不能只看语法。保留原 60 题作为历史监控，另设开发集与最终盲测集。分项报告，避免聊天改善掩盖代码回退；验收还需绝对最低能力要求，不能只与很弱的基线持平。
5. **底座路线保留对照。** 如果高质量小实验仍不能改善基本推理和代码，应优先评估成熟预训练骨干加 uTTT 适配模块。原 `.prompt/MAIN-PROMPT.md` 允许该路线；保留已预训的语言/FFN路径，渐进接入共享记忆，旧检查点不能直接作为新骨干权重加载，显存与精确元梯度必须重测。继续完全自训则需要更多高质量中英、代码和推理预训练，而非只扩大窄 SFT 步数。[训练计算与数据预算研究](https://arxiv.org/abs/2203.15556)

本轮完成的是只读诊断和具体实验设计，没有追加正式训练或更换服务模型。
