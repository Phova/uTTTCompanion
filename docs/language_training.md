# 语言质量诊断与下一轮训练

## 已确认的事实

现有 `Vitamin-C.pt` 实际包含 150,572,064 个独立参数，训练了 10,000 步。旧名称 `uTTT-500M-Base` 不是实际参数量；旧 `--large` 预设实际是 436,302,384 参数，也不是 800M。

该检查点从随机权重开始，在现有 ShareGPT 对话数据上训练。训练日志中的约 0.8 是字符/字节混合分词下的**训练集**交叉熵，不代表翻译、指令遵循或泛化能力。数据文件有 181,407 行，其中按原始整行计数有 169,245 个不同记录。原流程没有独立验证集。

实际权重的受控测试中，冻结和更新快权重的语料 CE 几乎相同，例如第 100 条分别为 1.2998 与 1.2994；关闭重复惩罚、使用贪婪解码后，翻译和简单算术仍答非所问。因此不能通过降低温度或降低惊奇度阈值修复已经学坏的语言能力。

使用新增评测工具对旧检查点测试，四个要求固定输出的基础指令严格匹配为 **0/4**；连同问候在内的五条输出都达到 64-token 上限，均未生成 EOS。这组小样例只用于复现当前问题，不是完整能力基准。

旧流程还存在以下质量缺陷：

- 每条长对话永远只训练开头窗口。抽查的四个 1024-token 窗口都没有 EOS，后续内容和结束行为缺少训练。
- 下载器丢弃小于 100 字符的短对话，简单问候等训练样本被排除；还人为添加推理时没有的类别“用户消息”。
- 英文按字节、中文主要按单字分词，1024-token 训练窗口能覆盖的英文内容很短。对字符直接施加 1.18 的重复惩罚会惩罚常用字母。
- 直接最小化由模型自己学习的 K/V 重建任务可以得到很小的惊奇度，却不保证记忆对语言任务有用。当前检查点的惊奇度约为 0.00004，低于 0.015 门限；降低门限不能补齐语言能力。

## 当前实现

1. 对整条对话去重并按内容哈希划分训练/验证集，再采样窗口。长回答的中后段也能被训练；先计算角色标签再裁剪，避免把用户消息当作回答监督。
2. 保留短样本，移除人为类别消息，并训练回答结束符。
3. 新增本地 byte-level BPE。特殊 token ID 固定为 0–5；词表完整嵌入检查点，旧检查点继续使用旧分词，二者不能混用。
4. 明确三个阶段：`pretrain` 学语言，`sft` 学回答指令，`meta` 学在线记忆。前两个阶段使用与冻结记忆生成一致的读出路径，且不执行未训练的在线 TTT 写入。`meta` 默认不直接最小化重建辅助损失，用验证集语言损失检查记忆是否有用。
5. 记录实际 token 数、验证 CE、冻结记忆的验证 CE，并额外导出 `.best.pt`。`deploy/evaluate_model.py` 独立检查实际生成与基础指令，不能只依据训练损失判断成功。
6. 移除因果训练中每层检查点输入对无用末尾快权重的保留，使同一张卡能训练更大的模型。
7. Linux/WSL 加载服务检查点及训练恢复使用内存映射，避免服务为未使用的巨量优化器状态分配主机内存。完整训练检查点仍然很大，保存时还需要足够的主机内存和磁盘。

验证包括 32 项自动测试，以及一个约 12 万参数小模型的受控学习实验：180 步后，五个已训练样例（问候、两种颜色指令、`hello→你好`、`1+1→2`）均正确生成，并均输出 EOS。这是训练/生成链路的正确性检查，不是未见任务上的泛化评测，也不代表旧检查点已被修复。

## 本机最大已验证候选

使用 RTX 5090、FP32 参数/梯度/AdamW 状态、BF16 激活、梯度检查点、batch=1、seq_len=1024、chunk=128、不量化、不卸载、关闭编译，对每个候选执行两步完整前向、反向和优化器更新。

| 参数量 | 宽度 / 层数 | 峰值预留显存 | 28 GiB 进程预算 |
|---:|---:|---:|---|
| 1,498,652,224 | 2560 / 32 | 26.58 GiB | 通过 |
| **1,583,879,748** | **2560 / 34** | **27.96 GiB** | **通过** |
| 1,626,493,510 | 2560 / 35 | 28.67 GiB | 超过预算 |

对应配置是 `configs/5090_max_config.yaml`，`--large` 也已更新到该规模。完整结果在 `docs/capacity_report.json`。这是该候选族、该上下文长度和该预算下的短程实测上限；改变长度、批量、编译方式或其他 GPU 工作负载需要重新测量，不代表训练越大质量就越好。

## 操作步骤

先更新代码并安装依赖。现有远端虚拟环境已经安装了 BPE 依赖；新环境需要运行环境初始化或安装 `requirements.txt`。

在本地 WSL 项目目录中，为下一轮模型准备词表：

```bash
./deploy/remote_ctl.sh prepare-tokenizer --data-path data/uttt_persona_train.jsonl
```

最好使用实际预训练语料训练词表，再将该词表固定用于全部阶段。分词器默认排除与训练器相同哈希规则下的 2% 验证样本。

若仅有现有对话语料，可以先用短程运行验证整条流程：

```bash
./deploy/remote_ctl.sh train --config configs/5090_max_config.yaml --stage pretrain --data-path data/uttt_persona_train.jsonl --steps 100 --output-ckpt checkpoints/uttt_pipeline_check.pt
```

这 100 步不构成语言预训练，也不应作为正式聊天模型。正式训练应先准备足量、干净、去重的广域中英文文本，以 `text` 字段 JSONL 或逐行文本提供给 `--data-path`。**把原对话集反复训练更多轮、或只增大到 15.84 亿参数，仍可能得到答非所问的模型。** 参数量与训练数据量需要共同扩展；这与 [Chinchilla 的原始研究](https://arxiv.org/abs/2203.15556) 一致，但其中的经验比例不能作为本自定义架构的质量保证。

预训练完成后，使用同一配置、同一词表，把 `--data-path` 换成高质量指令数据，并明确初始化来源与新的输出文件：

```bash
./deploy/remote_ctl.sh train --config configs/5090_max_config.yaml --stage sft --init-from checkpoints/uttt_pretrain.best.pt --data-path data/uttt_persona_train.jsonl --steps 3000 --output-ckpt checkpoints/uttt_sft.pt
./deploy/remote_ctl.sh evaluate --checkpoint checkpoints/uttt_sft.best.pt
```

`uttt_pretrain.best.pt` 是此示例假定的正式预训练输出，必须替换成实际文件。SFT 的 3000 步只是可调整的起点，应根据验证 CE 和实际问答选择检查点。达到语言质量要求后，再以 `--stage meta --init-from <SFT检查点>` 在长上下文和记忆任务上训练，输出到新的路径；只有该阶段的模型会启用在线 TTT。

现有 `Vitamin-C.pt` 的参数和分词仍可加载，但代码修复不会自动赋予已有权重新的语言知识。新 BPE 模型不能从该旧词表检查点直接恢复。
